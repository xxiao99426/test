# 核心代码讲解

面试时如果被问到「这块为什么这么写」，按本文回答。每节都给出**职责 → 关键实现 → 可能被追问的点**。

> 阅读顺序建议：`MarkerSpawner` → `ApiClient` → `InspectionUI` → `store.go` → `handlers.go`。这五个文件构成主链路，其余是配套。

---

## 1. Unity 端

### 1.1 `ProblemData.cs` —— 数据模型

**职责**：定义与后端共享的字段，以及 `priority` / `status` 两组枚举。

**关键点**

- 用 `[Serializable]` + 公开字段，是因为 `JsonUtility` 只认这个组合：不支持 `Dictionary`、不支持可空类型、不认属性。
- 因此 DTO 里所有字符串用 `""` 表示「没有」，而不是 `null`——`JsonUtility.FromJson` 遇到 `null` 字符串会给出 `null`，后续 `.Trim()` 直接空引用。
- `ProblemPriority.All = { "low", "medium", "high" }` 这个**数组顺序必须与 UI 按钮顺序一致**（`SceneBuilder` 建按钮时按同一顺序创建）。这是一条隐式契约，所以注释里写死了。
- `PositionDto(Vector3)` 构造函数负责 `float → double`：Unity 的坐标是 `float`，后端用 `double`，往返会掉精度，但要显式声明这个转换发生在哪。

**可能被问**：「为什么不用 Newtonsoft.Json？」
> 只为省事不值得多引一个包；`JsonUtility` 的字段名与 JSON 完全一致，而本题的数据结构没有任何 `JsonUtility` 处理不了的类型（没有字典、没有嵌套多态）。代价是数组根节点要包一层 `{"items":[...]}`，因为 `JsonUtility.FromJson<T[]>` 不支持顶层数组——`ApiClient` 里用 `ProblemListDto` 解决。

### 1.2 `ApiClient.cs` —— 网络层

**职责**：把 `UnityWebRequest` 包成「成功回调 + 失败回调」，并把技术错误翻译成人话。

**关键点**

1. **`UploadHandlerRaw` 必须显式 UTF-8 编码**
   ```csharp
   byte[] body = Encoding.UTF8.GetBytes(json);
   req.uploadHandler = new UploadHandlerRaw(body);
   ```
   漏了这一步，中文标题到后端会变乱码——`UnityWebRequest` 默认按系统编码处理原始字节。

2. **错误翻译是这一层的核心价值**
   ```csharp
   if (req.result == UnityWebRequest.Result.ConnectionError)
       return $"无法连接后端（{HostPort()}）。请确认 Go 服务已启动。";
   ```
   `req.error` 的原话是 `Cannot connect to destination host` 之类，对巡检员毫无意义。这里分三类：连不上 / 后端明确拒绝（解析后端 `ErrorBody` 拿到 `message`）/ 其他 HTTP 失败。

3. **回调式而不是 `async/await`**
   > `UnityWebRequest` 在协程里最稳；`async void` 在退出 Play 模式时抛出的异常不会被捕获，容易在 Console 里留一堆红字。用 `onSuccess/onError` 让调用方完全不接触协程。

4. **错误文案只保留 `host:port`**，不打完整 URL。这是实测改出来的：完整 URL 会把 440 px 宽的表单撑成三行，压到按钮上。

### 1.3 `MarkerSpawner.cs` —— 主链路（最核心）

**职责**：`点击 → 射线 → 命中点 → 标记`，同时守住三条硬约束。

**关键点**

1. **用 `hit.point`，不是 `bounds.center`**
   ```csharp
   Physics.Raycast(ray, out hit, maxDistance, blockingMask, QueryTriggerInteraction.Ignore);
   PlaceOrMovePending(hit.point, hit.normal);
   ```
   标记根节点的位置就是命中点，短杆沿 `hit.normal` 方向伸出，球头在杆顶。**肉眼就能看出标记钉在哪个点**，这也是自检能量化验证的前提（自检断言误差 < 1 mm，同时反证「距物体中心 > 0.2 m」）。

2. **`HandleClick(Vector2 screenPoint)` 为什么单独抽出来**
   > `Update` 只做一件事：把真实鼠标位置喂进来。抽出来的目的是让自检能直接喂 UI 控件的屏幕坐标，从而自动验证「点 UI 不穿透」。如果写成 `if (Input.GetMouseButtonDown(0)) { ... Input.mousePosition ... }`，这条规则就只能靠人点。

3. **UI 穿透拦截是双重判定**
   ```csharp
   // 一：EventSystem 标准射线
   EventSystem.current.RaycastAll(_uiProbe, _uiProbeResults);
   if (_uiProbeResults.Count > 0) return true;
   // 二：兜底几何判定
   return GeometryBlocksAt(screenPoint);
   ```
   为什么要兜底：`GraphicRaycaster` 会跳过 `Graphic.depth == -1` 的控件，而 `depth` 是画布**完成一次合批**时才被赋值的。画布刚 `SetActive(true)`、或当前没有任何一帧被渲染时，所有控件 `depth` 都是 `-1`，第一层判定必定返回空 —— 结果就是点击穿透、场景里多一个标记。这个 bug 是实测出来的（见 AI_LOG 第 2 条）。

4. **单标记状态机：移动而不是销毁重建**
   ```csharp
   if (_pending == null) _pending = CreateMarker(...);
   else _pending.transform.position = hitPoint;
   ```
   > 对象数量始终 ≤ 1，所以「一次有效点击最多一个待提交标记」在 Hierarchy 里是可数的，不需要开发者口头保证。

5. **`Physics.SyncTransforms()` 不能省**
   > Unity 2018.3 之后默认关闭 Auto Sync Transforms：代码改完 Transform，物理引擎的 broadphase 还是旧数据。表现就是**刚创建/刚移动的标记在接下来几帧点不中**，只能瞎点碰运气。创建后、移动后、改缩放后都要同步。

6. **取消时先 `SetActive(false)` 再 `Destroy`**
   > `Destroy` 要等到帧末才回收，中间这一帧物体仍可见、Collider 仍可被射线打中 —— 「已经取消了，下一秒还能点到一个幽灵标记」。`SetActive(false)` 让它立刻退出渲染与物理查询。

7. **`FacingRotation` 的 `up` 参考**
   > `Quaternion.LookRotation(forward, up)` 在 `forward` 与 `up` 平行时无解（地面法线就是竖直向上）。所以判断 `|dot(normal, up)| > 0.99` 时把参考向量换成 `Vector3.forward`。

8. **恢复标记统一竖直立起**
   > 后端只存坐标（第 4 节的数据结构没有法线字段），恢复时不能沿用「朝向法线」，否则贴墙标记的球头会沿 `+Z` 伸进柜体内部看不见。取舍：**坐标完全一致，朝向可能与首次放置略有差异**——这条写进了 README 的已知问题。

### 1.4 `MarkerVisual.cs` —— 标记外观

**关键点**

- **用 `MaterialPropertyBlock` 而不是 `renderer.material`**
  > 后者每次访问都会克隆一份材质实例，标记多了会持续泄漏内存，而且每个实例各占一个 draw call，合批被破坏。
- **配色优先级**：待提交（青绿）> 已解决（绿）> 优先级色（高红 / 中橙 / 低蓝）。已解决的优先级信息不重要了，状态优先。
- **脉动只给待提交标记**：`localScale = baseScale * (1 + 0.14 sin(...))`。注意 `_headBaseScale` 要在 `Configure` 时缓存一次，否则每帧基于上一帧缩放累乘，会越缩越小或越缩越大。

### 1.5 `InspectionUI.cs` —— 交互层

**关键点**

1. **引用全部在生成场景时绑定，运行时零 `Find`**
   > `SceneBuilder` 建完 UI 后直接赋值给 `InspectionUI` 的字段并保存场景。这样运行时不依赖名字查找，改名不会悄悄断链。
2. **提交中禁用「提交」和「取消」两个按钮**
   > 只禁用提交的话，用户可以在请求在途时点取消 → 标记被销毁 → 请求成功回调里 `CommitPending` 拿到 `null`，出现「后端有记录、场景里没标记」的不一致。
3. **失败时不关表单、不清草稿、不销毁标记**
   > 用户可以直接点「提交」重试，不需要重新找位置、重新填写。实测验证过：断开后端提交失败 → 重启后端 → 再点提交 → 成功写入。
4. **客户端校验只是减少往返**
   > 空标题在客户端先拦一次，但后端的 400 才是最终防线。两层都做，是因为 React 端和任何第三方调用方也走同一个后端。

### 1.6 `MarkerRestorer.cs` —— 恢复历史标记

- `Start` 里拉一次列表，逐条 `CreateSavedMarker`。
- **失败不阻塞用户**：后端没起来时只在右上角显示「历史问题加载失败」，场景照常可走，上报时会再给一次具体原因。
- 计数用 `_count` 统一维护，提交成功后 `NotifyProblemAdded()` 递增。**不这么做的话右上角会一直停在启动时的数字**，用户会以为提交没生效。

### 1.7 `PlayerController.cs` —— 漫游

- `CharacterController` + 重力，`isGrounded` 时把竖直速度压到 `-2f`，避免在斜坡上抖。
- **右键转视角是刻意的**：左键要用来放标记，如果左键同时转视角，任何一次视角拖动都会多出一个标记。
- pitch 限制 ±80°，防止万向锁与视角翻转。

### 1.8 `SceneBuilder.cs` —— 场景生成器（编辑器工具）

> 为什么用脚本生成场景而不是手工搭？
> ① 几十个 UI 元素的引用全靠拖拽，漏一个就是运行时空引用；② 场景出问题时能一条命令重建；③ **评审方可以读代码知道场景里到底有什么**，而不是打开一个二进制 `.unity` 文件靠猜。

- 材质用 `Standard`，`Metallic/Smoothness` 手工设；灯用一个平行光 + 环境光。
- 生成完 `EditorSceneManager.SaveScene` 并写入 `EditorBuildSettings.scenes`，保证打包时启动场景正确。
- 自检日志 `[Verify] 通过：引用完整，可点击场景物体 18 个` 是生成后立刻做的引用完整性检查。

### 1.9 `RuntimeSelfTest.cs` —— 23 项自动化断言

**设计要点（这是最能体现「会验证」的部分）**

1. **期望值不写死，用探针射线算出来**
   > 最初把期望落点写成机柜面板的固定坐标，结果面板比柜体凸出 5 cm，命中点停在前者上，实现正确却报失败 —— 测试比实现更脆弱。改成自检自己发一条同样的射线取 `probeHit.point` 作为期望值。
2. **每条断言都配一条反证**
   - 「标记位置 == 命中点」+「标记没有落在物体中心」（否则用 `bounds.center` 也能通过）
   - 「点击 UI 没有产生标记」+「场景坐标上能正常产生标记」（否则守卫写成 `return true` 也能通过）
3. **逐条打日志**：Console 里多行字符串会被折叠成首行，所以一条断言一行 `Debug.Log`，便于逐条核对。

覆盖：T1 落点精度（5 项）、T2 单标记状态机（2 项）、T3 取消回收（3 项）、T4 UI 穿透拦截（6 项）、T5 引用完整性（7 项）= **23 项**。

### 1.10 `ScreenshotUtil.cs` —— 取证工具

> 编辑器失焦时 Game View 不重绘，普通截图拿到的是旧帧（实测：连续四次截图字节数完全相同）。这里把相机渲染到 `RenderTexture`，再把 UI 画布合进去，最后 `ReadPixels` 存 PNG —— 不依赖窗口是否可见。

## 2. Go 后端

### 2.1 `store.go` —— 持久化

**四条值得讲的决策**

1. **先写盘成功，再替换内存**
   ```go
   if err := s.persistLocked(next); err != nil { return err }
   s.items = next
   ```
   > 反过来的话，写盘失败时内存里已经有这条数据，健康检查、列表接口都能看到它，重启后却消失 —— 典型的「假成功」。

2. **写盘用「临时文件 → `Sync` → 原子重命名」**
   > 直接覆盖原文件，如果进程在写入中途被杀，会留下半截 JSON，下次启动直接解析失败。`Sync` 保证数据真的落盘（否则断电可能得到 0 字节文件），`Rename` 在 Windows 上是 `MoveFileEx + REPLACE_EXISTING`，天然原子。

3. **`List()` 返回切片副本**
   > 否则调用方拿到内部切片，可以在锁外改动/追加，锁就白加了。

4. **一把 `sync.RWMutex` 而不是更复杂的方案**
   > 数据量是几十到几百条，读写都极快。选简单的方案是为了让「为什么并发安全」能一句话说清：所有访问路径都在锁内，写操作要么整体成功要么整体不生效。

### 2.2 `handlers.go` —— 接口层

- **路由用 Go 1.22+ 的方法路由**：`mux.HandleFunc("PATCH /api/problems/{id}/status", ...)`，`{id}` 直接从 `r.PathValue("id")` 取，不需要第三方路由库。
- **`DisallowUnknownFields`**：字段名写错（`prio` 而不是 `priority`）会立刻 400，而不是被静默忽略、用默认值存进去。这类问题在联调期最难查。
- **`validateCreate` 一次只报第一个错误**：客户端修完一个再提交，出错信息永远指向当前要改的地方。返回 `{code, message, field}`，`field` 精确到 `position.x`。
- **状态码语义**：新建 201、查询/更新 200、参数错 400、id 不存在 404。

### 2.3 `main.go` —— 启动与退出

- 所有超时（读头 5s / 读写 15s / 空闲 60s）显式设置，不用零值（零值表示永不超时，慢连接会一直占着）。
- `SIGINT/SIGTERM` 优雅退出：给在途请求 5 秒收尾，避免写盘写一半被强杀。

### 2.4 `handlers_test.go` —— 11 个用例

覆盖：健康检查、创建成功（含中文）、空标题 400、非法 priority 400、缺 position 400、未知字段 400、列表返回、改状态成功、非法状态 400、id 不存在 404、**重启后数据仍在**（新建 store 指向同一文件再读）。

## 3. React 管理端

### 3.1 `api.ts` —— 请求封装

- `fetch` 只在**网络层失败**时抛异常（后端没起、DNS 失败、CORS 被拦），HTTP 4xx/5xx 不会抛。所以封装里要显式检查 `res.ok`，并把后端的 `ErrorBody.message` 提出来。
- 统一抛 `ApiError(code, message)`，UI 层只负责显示 `message`。

### 3.2 `App.tsx` —— 列表与状态流转

- **乐观更新 + 失败回滚**
  ```tsx
  setProblems(cur => cur.map(p => p.id === target.id ? {...p, status: next} : p))
  try { const updated = await updateProblemStatus(id, next); /* 用后端返回值覆盖 */ }
  catch { /* 回滚到 previous，并显示错误条 */ }
  ```
  > 网络慢时下拉框立刻响应，不会觉得卡；失败再退回原值，不会出现「界面显示已解决、后端还是待处理」的假象。
- **`busy` 用 ref 而不是 state**：防止自动刷新定时器在提交过程中触发，导致列表被旧数据覆盖。
- **后端不可用时**：整页不白屏，顶部出现红色错误条 + 「重试」按钮，表格保留最后一次成功的数据。这是必做项 3.2 第 4 条。

## 4. 三端为什么能对上

字段名单只有一份（第 4 节），三端各自映射到自己的类型：

| 概念 | Go | React | Unity |
|---|---|---|---|
| 问题 | `Problem` struct | `Problem` interface | `ProblemDto` class |
| 坐标 | `Position{X,Y,Z float64}` | `{x,y,z: number}` | `PositionDto{X,Y,Z double}` |
| 优先级 | `string` 常量 | 联合类型 `Priority` | `string` + `ProblemPriority.All` |
| 时间 | `time.Time`（RFC3339） | `string` 直接展示 | `string` 解析后本地化 |

两条经验：

1. **枚举值只在 Go 里定义一次**，另外两端是字符串常量 + 校验，不做双向映射表（映射表是 bug 温床）。
2. **坐标用 `double` 传输**，Unity 端在 `PositionDto` 构造函数里做 `float → double`，避免在业务层散落隐式转换。
